## 1. Purpose and Background

This system tracks classroom camera opt-in/opt-out compliance for BCPS under Florida Policy 4900 (HB 149). Every classroom requires 100% parent opt-in before a security camera can be installed and activated. Even one parent opting out blocks the camera.

The pipeline processes daily CSV reports from the district (generated by staff member Stephanie), merges them into a master Excel tracking file, detects approval status changes, and generates alerts for the ESE team.

**Key compliance requirements**:
- 100% parent opt-in required for camera authorization
- Cameras must be deactivated immediately if approval is lost
- Missing classrooms with active cameras are critical alerts
- 30-day installation deadline once approved

## 3. Pipeline Overview

The system is a three-phase pipeline:

```
Raw CSV Report  -->  Task 1  -->  Validation  -->  Task 2  -->  Master Excel
(from Stephanie)    (clean)      (quality check)   (merge)     (tracking file)
```

**Phase 1 - Task 1** (`task1_process_reports.py`):
- Reads raw `MM-DD-YYYY_Policy4900.csv` files
- Strips grey-shaded header rows (Excel artifacts)
- Normalizes column names, cleans data
- Calculates initial Approval Status from opt-in/out counts
- Writes `*_PROCESSED.csv` and `.step1` marker

**Phase 1.5 - Validation** (`validate_processed_data.py`):
- Schema validation (required columns, data types)
- Row count consistency checks
- Percentage field validation (0-100%)
- Student count balance (opt in + opt out + no response = total)
- Duplicate detection
- Cross-file anomaly detection (swing detection between reports)
- Writes `.validated_ok` marker if passed

**Phase 2 - Task 2** (`task2_merge_to_master_with_timeline.py`):
- Consumes pending Change Ack values (standalone, runs even without new reports)
- Finds `*_PROCESSED.csv` files with `.step1` but no `.step2`
- Backs up master before processing
- Loads master with retention rehydration
- For each report (chronological order):
  - Merges report data into master
  - Detects approval transitions (gained/lost)
  - Handles missing classrooms
  - Applies void overrides
  - Calculates approval status with override precedence
  - Saves master and updates retention file
  - Creates `.step2` marker
- Generates approval timeline and action reports

**Orchestrator** (`orchestrator_policy4900.py`):
- Runs all three phases in sequence
- Stops on failure (non-zero exit code)
- Supports `--step1`, `--step2`, `--dry-run`, `--validate`, `--no-validate` flags

## 7. Key Algorithms and Business Rules

### Approval Status Calculation

Calculated in `calculate_approval_status()` from student count data:

```
Priority order:
1. Mark if Void contains "void"  -->  "Void"
2. FISH List == "N"              -->  "Ineligible - FISH List N"
3. Total Student Count == 0      -->  "Not Requested"
4. Any students opted out > 0    -->  "Denied - Parent Opt Out"
5. All students opted in         -->  "Approved - Camera Authorized"
6. Any "No Response" remaining   -->  "Awaiting Responses"
7. Otherwise                     -->  "Not Requested"
```

**Critical rule**: 100% opt-in required. Even 1 opt-out = Denied.

### Approval Status Override Precedence

After the base calculation, overrides are applied in priority order:
1. **Void** (highest) - Room is out of the program entirely
2. **FISH List N** - Structural impossibility, cannot install camera
3. **Approval Lost** (unacknowledged) - Only if not Void or FISH N
4. **Calculated status** (lowest) - Normal operation

### Merge Algorithm (`merge_report_into_master`)

For each classroom in the new report:

1. **Build key index**: `master_idx_by_key = {key: positional_index for enumerate(df_master["key_sf"])}`
2. **Existing classroom** (key found in master):
   a. Calculate old approval status from current master data
   b. Update non-protected columns from report
   c. Calculate new approval status from updated data
   d. Detect transitions:
      - **Transition gained**: old != Approved, new == Approved
      - **Transition lost**: old == Approved, new != Approved
   e. If transition: set Change Control to "Approval Gained"/"Approval Lost", clear old ACK
   f. If no transition and ACK set: consume ACK (clear Change Control to "No Change", clear ACK)
   g. If no transition, no ACK, and existing alert: keep alert sticky
   h. If no transition, no ACK, no alert: set "No Change" or "Status Changed"
   i. Apply override precedence
3. **New classroom** (key not in master): Append with Change Control = "Added"

After processing all report rows:

4. **Void overrides**: Apply manual void overrides from `void_overrides.csv`
5. **Missing classrooms**: For each master row NOT in the new report:
   - Clear any ACK
   - Skip void rows
   - Classify as Missing - Camera Active/Installed/Pending/No Camera based on installation/activation status

### Merge Key Construction

Two key formats exist (historical reasons, both use single pipe internally):
- **Primary**: `school_name|room_number` (lowercased)
- **Fallback** (when room is empty): `school_name|fish_number` (lowercased)

The `_key()` method uses double-pipe (`||`) for void override keys, while `_mk_key_frame()` uses single-pipe (`|`) for merge keys. These never cross systems.

## 8. Marker File System

Marker files prevent reprocessing and track pipeline state:

| Marker | Created By | Purpose |
|--------|-----------|---------|
| `MM-DD-YYYY_Policy4900.csv.step1` | Task 1 | Indicates report has been processed into `*_PROCESSED.csv` |

**Task 1** looks for raw CSVs without `.step1` markers.
**Validation** looks for `*_PROCESSED.csv` without `.validated_ok` markers.

**To reprocess a report**: Delete its `.step2` marker (and `.step1` if you want to re-run Task 1).

## 9. Change Control and ACK System

### Change Control Values

| Value | Meaning | Sticky? |
|-------|---------|---------|
| Added | New classroom first appeared | No |
| Approval Gained | Changed TO "Approved - Camera Authorized" | Yes - until ACK |
| Approval Lost | Changed FROM "Approved - Camera Authorized" | Yes - until ACK |
| Status Changed | Approval status changed (non-gain/loss) | No |
| No Change | Status unchanged from last report | No |
| Missing - Camera Active | Not in report but camera is active (CRITICAL) | No |
| Missing - Camera Installed | Not in report but camera is installed | No |
| Missing - Camera Pending | Not in report but was pending approval | No |
| Missing - No Camera | Not in report, no camera installed | No |

### Sticky Alerts

"Approval Gained" and "Approval Lost" are **sticky** -- they persist across reports until the user acknowledges them. This ensures alerts are not missed between pipeline runs.

### ACK (Acknowledgment) Workflow

1. Pipeline runs, detects transition, sets Change Control = "Approval Gained" or "Approval Lost"
2. User opens master Excel file and sees the alert
3. User types **"ACK"** in the Change Ack column for that row
4. User saves the Excel file
5. Next pipeline run: ACK is consumed
   - Change Control resets to "No Change"
   - Change Ack is cleared to empty
   - The alert is dismissed

**Important**: ACK consumption runs at the START of every Task 2 execution, even when there are no new reports to process. This ensures acknowledgments take effect immediately on the next run.

### How ACK Consumption Works (Technical)

The `consume_pending_acks()` method runs before checking for new reports:
1. Loads master file
2. Finds all rows where Change Ack is not empty
3. Sets Change Control = "No Change" and Change Ack = "" for each
4. Saves master file

Additionally, during report merging, ACK is also consumed inline:
- If no approval transition occurred and ACK is set: consume ACK, set "No Change"
- If a NEW transition occurred and old ACK exists: clear old ACK (new alert takes over)
- For missing classrooms: always clear ACK

## 10. Retention System

The retention system ensures installed/active cameras are never lost from the master file, even if the master is rebuilt from scratch.

### How It Works

1. After each report merge, `_update_retention_file()` saves all classrooms with installed or active cameras to `Policy4900_Retained.csv`
2. When `load_master()` runs, it reads the master Excel AND the retention CSV
3. It concatenates them: `pd.concat([master, retained], ignore_index=True)`
4. Deduplicates: `drop_duplicates(subset=["key_sf"], keep="first")` -- master data wins

### What's Excluded from Retention

Change-tracking columns are excluded because they are temporary:
- Change Ack
- Change Control
- Change First Seen
- Last Status Change
- Last Fully Approved Date
- Days Since Fully Approved

### Camera Detection

A classroom is considered installed/active if ANY of these match (case-insensitive, substring matching):
- Activation Status contains "activat" or "active"
- Installation Status contains "install"
- A camera-related status like "pending", "scheduled"

## 11. Void Override System

### Purpose

Some classrooms need to be permanently excluded from tracking (e.g., rooms that no longer exist, administrative spaces incorrectly included).

### How It Works

1. Edit `C:\BCPS\ESE\Void_Schools\void_overrides.csv` with columns: School of Instruction, Room
2. During merge (Step 2 of the merge algorithm), each master row is checked against void keys
3. Matching rows get:
   - Mark if Void = "Void"
   - Approval Status recalculated (returns "Void" because of the Mark if Void check)
   - Override precedence applied (Void is highest priority)

### Also in Master

Users can also manually type "Void" (case-insensitive) in the "Mark if Void" column directly in the master Excel file. The pipeline respects this on every run.

### Void and Missing Classrooms

Void classrooms that disappear from reports are NOT flagged as "Missing". The pipeline skips them during the missing-classroom check (they're explicitly out of scope).

## 16. Troubleshooting

### "No new reports found" (Task 1)
- Check that CSV file is in: `C:\BCPS\ESE\Policy4900_Reports_New\`
- Verify filename format: `MM-DD-YYYY_Policy4900.csv`
- Check that `.step1` marker doesn't already exist (delete it to reprocess)

### "No new reports to process" (Task 2)
- Run Task 1 first
- Check that `.step1` markers exist for processed files
- Check that `.step2` markers don't already exist (delete to reprocess)
- Note: ACK consumption still runs even with this message

### "BLOCKED - Critical errors found" (Validation)
- Check validation artifacts in `C:\BCPS\ESE\Validation_Artifacts\`
- Common causes: missing columns, corrupted data, non-numeric values in count fields
- Fix the source data and reprocess from Task 1

### Excel file won't open / is corrupted
- Check backups in `C:\BCPS\ESE\Backups\Policy4900_Reports_Master\`
- Use `python utilities/backup_manager.py` to list and restore backups
- Use `python utilities/fix_excel_file.py <path>` to attempt repair of corrupted files

### ACK not being consumed
- ACK is consumed at the start of every Task 2 run, even without new reports
- Make sure you saved the Excel file after typing "ACK"
- Make sure the Excel file is closed before running the pipeline (file lock)
- Run: `python task2_merge_to_master_with_timeline.py`

### File locked by Excel
- Close the master Excel file before running the pipeline
- If the pipeline fails mid-write, the data should still be saved (formatting may be missing)

## 18. Bug Fix History


### ACK Never Consumed (Fixed Feb 2026)

**Bug**: User types "ACK" in the Change Ack column, but it never gets consumed.

**Root Cause**: ACK consumption was exclusively inside `merge_report_into_master()`, which only runs when there are new reports. Without new reports, the pipeline exits immediately at the "No new reports to process" check, and the master file is never touched. The user's typical workflow (add ACK between pipeline runs, no new report available) meant ACK was never processed.

**Fix**: Added `consume_pending_acks()` method that runs at the start of every Task 2 execution, before checking for new reports. This loads the master, finds all ACK values, clears both Change Control (to "No Change") and Change Ack (to empty), and saves the master.

## 19. Technical Deep-Dive (for AI assistants)

This section contains implementation details useful for debugging and modifying the code.

### DataFrame Indexing Pattern

The merge function builds a key-to-index mapping using `enumerate()`:
```python
master_idx_by_key = {k: i for i, k in enumerate(df_master["key_sf"])}
```

All subsequent `.at[i, col]` calls use these positional indices. This works correctly because `load_master()` uses `pd.concat([df, keep], ignore_index=True)` followed by `drop_duplicates(subset=["key_sf"], keep="first")`. Since retained rows are appended at the end and duplicates are removed from the end, the resulting index is always contiguous (0 to N-1), making positional indices match label indices.

**Caution**: If `drop_duplicates` ever removes rows from the middle (not just the end), the index would have gaps, causing `.at[i, col]` to access wrong rows or raise KeyError. This hasn't happened in practice because master rows always come first in the concat.

### Protected Columns

Protected columns are defined in `__init__`:
```python
self.protected_columns = [
    "Date First Seen", "Date Added to Installation List",
    "Installation Status", "Installation Date",
    "Activation Status", "Activation Date",
    "Camera Source School", "Camera Source Classroom",
    "Camera Type", "Notes",
    "Change Ack", "Change Control", "Authorized Date"
]
```

During merge, when copying data from the report to master, protected columns are skipped:
```python
for col in self.master_columns:
    if col in row.index and col not in self.protected_columns:
        val = row[col]
        if pd.notna(val) and str(val).strip() != "":
            df_master.at[i, col] = val
```

### String Handling for NaN

All string columns in the master are cast to string with NaN filled during `load_master()`:
```python
df[col] = df[col].fillna("").astype(str)
```

When reading values, the pattern `str(value or "").strip()` is used as a safety net. Note: `float('nan') or ""` returns `nan` (truthy), so `str(nan)` = `"nan"`. However, since `fillna("")` runs during load, this case shouldn't occur in practice.

### File Write Sequence

`_write_master()` performs two writes:
1. `pd.ExcelWriter` with openpyxl writes the data and percentage formatting
2. `_apply_excel_formatting()` reopens the file with `load_workbook`, adds conditional formatting, and saves

If step 2 fails (e.g., file locked), the data from step 1 is still saved correctly. The exception propagates up but the data is intact.

### Retention File Columns

The retention CSV excludes these columns:
```python
exclude_from_retention = {
    "Change Ack", "Change Control", "Change First Seen",
    "Last Status Change", "Last Fully Approved Date",
    "Days Since Fully Approved"
}
```

When the retention file is rehydrated into the master via `load_master()`, these columns will be NaN for retained rows (then filled to "" by the string casting). This means retained cameras start with clean change-tracking state on each load.

### Key Differences: _key() vs _mk_key_frame()

- `_key(school, room)` returns `school||room` (double pipe, used for void overrides set lookup)
- `_mk_key_frame(df)` returns a Series of `school|room` (single pipe, used for merge key column)
- These two key systems never interact, so the separator difference is harmless
